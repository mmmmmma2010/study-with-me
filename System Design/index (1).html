موازنة الأحمال والـ Caching بعمق (Load Balancing & Caching)

ستتعلم كيف توزّع الطلبات بذكاء، وكيف تجعل النظام أسرع 10 مرات بدون أن تعرض بيانات قديمة.

الدرس 2 من 8 المستوى: متوسط اللغة: Python وقت القراءة: 40 دقيقة

📚 محتوى الدرس

مقدمة تشبيه من الحياة المصطلحات الأساسية المفاهيم الأساسية كيف يعمل من الداخل أمثلة الكود الأخطاء الشائعة أفضل الممارسات الأداء والموازنات مشروع تطبيقي اختبر نفسك تمارين الخلاصة الخطوة التالية

مقدمة

📝 تذكير من الدرس 1: تعلمنا أن التوسع الأفقي يحتاج موازن أحمال، وأن قاعدة البيانات غالبًا هي عنق الزجاجة. في هذا الدرس نحل المشكلتين.

بوابة الدفع عندنا تقرأ إعدادات التاجر في كل عملية دفع. اسم التاجر، ونسبة العمولة، وطرق الدفع المفعّلة. هذه البيانات نادرًا ما تتغير، لكننا نقرأها آلاف المرات في الثانية.

لماذا نسأل قاعدة البيانات كل مرة عن شيء نعرف جوابه؟ هنا يأتي دور الـ Cache. وحتى نوزّع الطلبات على الخوادم بعدل، نحتاج موازن أحمال ذكيًا.

في هذا الدرس ستتعلم:

  • الفرق بين موازن الطبقة الرابعة والطبقة السابعة (L4 / L7).
  • خوارزميات التوزيع، ومنها التجزئة المتسقة (Consistent Hashing).
  • استراتيجيات الـ Cache: متى نقرأ، ومتى نكتب، ومتى نحذف.
  • سياسات الإخراج (Eviction) مثل LRU.
  • ثلاث مشاكل خطيرة: التدافع، والاختراق، والانهيار الجماعي.

تشبيه من الحياة

📚 تخيّل مكتبة جامعية كبيرة.

المخزن الرئيسي في القبو فيه كل الكتب. لكن الوصول إليه يأخذ 10 دقائق. هذا هو قاعدة البيانات.

أمين المكتبة يضع الكتب الأكثر طلبًا على رف قريب من المكتب. يأخذها في 10 ثوانٍ. هذا الرف هو الـ Cache.

الرف صغير. عندما يمتلئ، يعيد أمين المكتبة إلى القبو الكتاب الذي لم يطلبه أحد منذ أطول وقت. هذه هي سياسة LRU.

إذا صدرت طبعة جديدة من كتاب، يجب أن يسحب أمين المكتبة الطبعة القديمة من الرف. وإلا سيقرأ الطلاب معلومات قديمة. هذا هو إبطال الـ Cache (Invalidation).

وفي المدخل موظف استقبال يوجّه كل طالب إلى أمين مكتبة غير مشغول. هذا هو موازن الأحمال.

المفاهيم الأساسية

الجزء الأول: موازنة الأحمال

1. الطبقة الرابعة مقابل الطبقة السابعة

موازن L4 يرى فقط: "اتصال من هذا العنوان إلى هذا المنفذ". لا يفتح الطلب. لذلك هو سريع جدًا ورخيص.

موازن L7 يقرأ طلب HTTP كاملًا. يستطيع أن يرسل /payments إلى خوادم الدفع، و /reports إلى خوادم التقارير. لكنه أبطأ قليلًا لأنه يفك التشفير (TLS) ويقرأ المحتوى.

flowchart LR C["Client"] --> L7["L7 Load Balancer"] L7 -- "/payments" --> P1["Payments 1"] L7 -- "/payments" --> P2["Payments 2"] L7 -- "/reports" --> R1["Reports 1"] L7 -- "/static" --> CDN["CDN"]

2. خوارزميات التوزيع

الخوارزميةكيف تعملمتى تستخدمها

3. فحص الصحة النشط والسلبي

الفحص النشط (Active): الموازن يرسل طلبًا إلى /health كل بضع ثوانٍ. إذا فشل 3 مرات متتالية، يخرج الخادم من الخدمة.

الفحص السلبي (Passive): الموازن يراقب الطلبات الحقيقية. إذا رجعت أخطاء 5xx كثيرة من خادم، يوقف الإرسال إليه مؤقتًا. الأفضل أن تستخدم النوعين معًا.

الجزء الثاني: الـ Caching

4. أين نضع الـ Cache؟

يوجد Cache في كل طبقة تقريبًا. كلما اقترب من المستخدم، صار أسرع. لكن التحكم فيه يصبح أصعب.

flowchart LR B["Browser Cache"] --> CDN["CDN"] CDN --> LB["Load Balancer"] LB --> APP["App: Local Cache"] APP --> RED[("Distributed Cache - Redis")] RED --> DB[("Database + Buffer Pool")]
  • Cache محلي داخل الخادم: أسرع شيء، بدون شبكة. لكن كل خادم عنده نسخة مختلفة، وإبطاله صعب.
  • Cache موزّع مثل Redis: كل الخوادم تشترك فيه. يحتاج رحلة شبكة، حوالي 1ms.

5. استراتيجيات القراءة والكتابة

الاستراتيجيةكيف تعملالميزةالعيب
Cache-Asideالتطبيق يسأل الـ Cache. عند الإخفاق يقرأ من قاعدة البيانات ويحفظ النتيجة.بسيطة. الـ Cache يحتوي فقط ما نحتاجه.أول طلب دائمًا بطيء.
Read-Throughالـ Cache نفسه يقرأ من قاعدة البيانات عند الإخفاق.كود التطبيق أبسط.يحتاج مكتبة أو خدمة تدعمه.
Write-Throughنكتب في الـ Cache وقاعدة البيانات معًا.الـ Cache دائمًا محدّث.الكتابة أبطأ.
Write-Behindنكتب في الـ Cache فقط، ثم نرسل إلى قاعدة البيانات لاحقًا.كتابة سريعة جدًا.⚠️ قد تضيع البيانات إذا توقف الـ Cache.
Write-Aroundنكتب في قاعدة البيانات فقط، ونترك الـ Cache.لا نملأ الـ Cache ببيانات لن تُقرأ.أول قراءة بعد الكتابة بطيئة.
⚠️ تحذير: لا تستخدم Write-Behind لبيانات الدفع أبدًا. عملية دفع ضاعت لأن الـ Cache أعيد تشغيله تعني أموالًا ضائعة.

6. سياسات الإخراج

  • LRU (Least Recently Used): نحذف العنصر الذي لم يُستخدم منذ أطول وقت. هذه هي الأكثر شيوعًا.
  • LFU (Least Frequently Used): نحذف العنصر الأقل استخدامًا في المجموع.
  • FIFO: نحذف الأقدم دخولًا، بغض النظر عن الاستخدام.
  • TTL: ليست سياسة إخراج بالضبط. العنصر ينتهي بعد مدة محددة، حتى لو كان الـ Cache فارغًا.

7. أصعب مشكلة: الإبطال

يوجد قول مشهور: "أصعب شيئين في علوم الحاسوب: إبطال الـ Cache، وتسمية الأشياء". المشكلة أن لديك الآن نسختين من البيانات. وأي اختلاف بينهما يعني أن المستخدم يرى بيانات قديمة.

القاعدة العملية مع Cache-Aside: حدّث قاعدة البيانات أولًا، ثم احذف المفتاح من الـ Cache. لا تحدّث الـ Cache بالقيمة الجديدة. احذفه فقط، والقراءة التالية تملؤه. وضع دائمًا TTL كشبكة أمان.

كيف يعمل من الداخل

تدفق Cache-Aside

لماذا "حدّث ثم احذف" وليس العكس؟

انظر ماذا يحدث إذا حذفنا من الـ Cache قبل تحديث قاعدة البيانات، وجاء قارئ في المنتصف:

sequenceDiagram participant W as Writer participant R as Reader participant C as Cache participant DB as Database W->>C: DELETE merchant:m1 R->>C: GET merchant:m1 C-->>R: miss R->>DB: read fee DB-->>R: fee = 2.5 (old) W->>DB: UPDATE fee = 2.0 R->>C: SET fee = 2.5 Note over C: Stale until TTL expires!

القارئ قرأ القيمة القديمة قبل التحديث، ثم وضعها في الـ Cache بعد الحذف. الآن الـ Cache يعرض العمولة القديمة حتى تنتهي الـ TTL. مع ترتيب "حدّث ثم احذف"، هذه المشكلة نادرة جدًا. والـ TTL تحميك في الحالة النادرة.

مثال 1: LRU Cache باستخدام OrderedDict

from collections import OrderedDict


class LRUCache:
    def __init__(self, capacity: int) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self._data: OrderedDict[str, str] = OrderedDict()
        self.hits = 0
        self.misses = 0

    def get(self, key: str) -> str | None:
        if key not in self._data:
            self.misses += 1
            return None
        self._data.move_to_end(key)       # mark as most recent
        self.hits += 1
        return self._data[key]

    def put(self, key: str, value: str) -> None:
        if key in self._data:
            self._data.move_to_end(key)
        self._data[key] = value
        if len(self._data) > self.capacity:
            evicted, _ = self._data.popitem(last=False)  # oldest
            print(f"evicted: {evicted}")


cache = LRUCache(capacity=2)
cache.put("m1", "Merchant One")
cache.put("m2", "Merchant Two")
cache.get("m1")                     # m1 becomes most recent
cache.put("m3", "Merchant Three")   # no room: evict oldest
print(cache.get("m2"))
print(cache.get("m1"))
print(f"hits={cache.hits} misses={cache.misses}")
evicted: m2 None Merchant One hits=2 misses=1

الشرح سطرًا بسطر

  1. OrderedDict: قاموس يحفظ ترتيب العناصر. أول عنصر هو الأقدم.
  2. move_to_end(key): عند كل استخدام، ننقل العنصر إلى النهاية. يصبح "الأحدث".
  3. len(self._data) > self.capacity: إذا تجاوزنا السعة، يجب أن نحذف عنصرًا.
  4. popitem(last=False): نحذف من البداية، أي الأقدم استخدامًا.
  5. بعد get("m1") صار الترتيب m2, m1. لذلك خرج m2 وليس m1.

مثال 2: Cache-Aside مع TTL وإبطال

نستخدم ساعة مزيفة (Fake Clock) حتى نتحكم في الوقت أثناء الاختبار. هذه حيلة مهمة لاختبار أي كود فيه TTL.

class FakeDB:
    def __init__(self) -> None:
        self.rows = {"m1": {"name": "Cairo Store", "fee": 2.5}}
        self.reads = 0

    def get_merchant(self, mid: str) -> dict | None:
        self.reads += 1
        row = self.rows.get(mid)
        return dict(row) if row else None   # return a copy

    def update_fee(self, mid: str, fee: float) -> None:
        self.rows[mid]["fee"] = fee


class TTLCache:
    def __init__(self, clock) -> None:
        self._data: dict[str, tuple[dict, float]] = {}
        self.clock = clock

    def get(self, key: str) -> dict | None:
        item = self._data.get(key)
        if item is None:
            return None
        value, expires_at = item
        if self.clock() >= expires_at:
            del self._data[key]
            return None
        return value

    def set(self, key: str, value: dict, ttl: float) -> None:
        self._data[key] = (value, self.clock() + ttl)

    def delete(self, key: str) -> None:
        self._data.pop(key, None)


now = [0.0]


def clock() -> float:
    return now[0]


db = FakeDB()
cache = TTLCache(clock)


def get_merchant(mid: str) -> dict | None:
    key = f"merchant:{mid}"
    cached = cache.get(key)
    if cached is not None:
        return cached
    row = db.get_merchant(mid)
    if row is not None:
        cache.set(key, row, ttl=60)
    return row


def update_fee(mid: str, fee: float) -> None:
    db.update_fee(mid, fee)            # 1) update the source of truth
    cache.delete(f"merchant:{mid}")    # 2) then invalidate


for _ in range(3):
    get_merchant("m1")
print("db reads after 3 calls:", db.reads)

update_fee("m1", 2.0)
print("fee:", get_merchant("m1")["fee"], "| db reads:", db.reads)

now[0] = 61                            # jump past the TTL
get_merchant("m1")
print("db reads after TTL:", db.reads)
db reads after 3 calls: 1 fee: 2.0 | db reads: 2 db reads after TTL: 3

الشرح سطرًا بسطر

  1. return dict(row): نرجع نسخة. لو أرجعنا نفس الكائن، سيتغير الـ Cache مع قاعدة البيانات بالخطأ، ونظن أن الإبطال يعمل وهو لا يعمل.
  2. (value, self.clock() + ttl): نحفظ القيمة مع وقت انتهائها.
  3. if self.clock() >= expires_at: إذا انتهت الصلاحية، نحذف ونعتبرها إخفاقًا.
  4. ثلاث قراءات، لكن قاعدة البيانات قُرئت مرة واحدة. الاثنتان الأخريان من الـ Cache.
  5. update_fee: نحدّث قاعدة البيانات أولًا، ثم نحذف المفتاح. القراءة التالية تجلب 2.0 الجديدة.
  6. now[0] = 61: نقفز في الزمن. الـ TTL انتهت، فنقرأ من قاعدة البيانات مرة أخرى.

مثال 3: لماذا التجزئة المتسقة؟

عندك 4 خوادم Cache. الطريقة البسيطة: hash(key) % 4. ماذا يحدث إذا أضفت خادمًا خامسًا؟

import bisect
import hashlib


def h(value: str) -> int:
    return int(hashlib.md5(value.encode()).hexdigest(), 16)


class HashRing:
    def __init__(self, nodes: list[str], vnodes: int = 200) -> None:
        self.vnodes = vnodes
        self._points: list[int] = []      # sorted positions on the ring
        self._owner: dict[int, str] = {}  # position -> node
        for node in nodes:
            self.add(node)

    def add(self, node: str) -> None:
        for i in range(self.vnodes):
            point = h(f"{node}#{i}")
            bisect.insort(self._points, point)
            self._owner[point] = node

    def get(self, key: str) -> str:
        idx = bisect.bisect(self._points, h(key)) % len(self._points)
        return self._owner[self._points[idx]]


def mod_n(key: str, nodes: list[str]) -> str:
    return nodes[h(key) % len(nodes)]


keys = [f"payment:{i}" for i in range(10_000)]
old_nodes = ["cache-1", "cache-2", "cache-3", "cache-4"]
new_nodes = old_nodes + ["cache-5"]

moved_mod = sum(mod_n(k, old_nodes) != mod_n(k, new_nodes) for k in keys)

ring = HashRing(old_nodes)
before = {k: ring.get(k) for k in keys}
ring.add("cache-5")
after = {k: ring.get(k) for k in keys}
moved_ring = [k for k in keys if before[k] != after[k]]
only_to_new = all(after[k] == "cache-5" for k in moved_ring)

print(f"mod-N moved : ~{round(100 * moved_mod / len(keys), -1):.0f}%")
print(f"ring moved  : ~{round(100 * len(moved_ring) / len(keys), -1):.0f}%")
print(f"moved keys all went to cache-5: {only_to_new}")
mod-N moved : ~80% ring moved : ~20% moved keys all went to cache-5: True

الشرح سطرًا بسطر

  1. h(value): نحوّل النص إلى رقم كبير ثابت. نستخدم md5 لأن hash() في Python يتغير مع كل تشغيل.
  2. vnodes=200: كل خادم يظهر 200 مرة على الحلقة. هذه "العُقد الافتراضية" (Virtual Nodes). بدونها يكون التوزيع غير متساوٍ.
  3. bisect.insort: نضيف النقطة مع الحفاظ على الترتيب.
  4. bisect.bisect(...): نبحث عن أول نقطة بعد مفتاحنا، في اتجاه عقارب الساعة. صاحب هذه النقطة هو الخادم المسؤول.
  5. % len(self._points): إذا وصلنا إلى نهاية الحلقة، نرجع إلى البداية.
  6. round(..., -1): نقرّب إلى أقرب 10%، لأن الرقم الدقيق يتغير قليلًا حسب التجزئة.
  7. النتيجة: مع mod N تحرّك 80% من المفاتيح. هذا يعني أن 80% من الـ Cache صار بلا فائدة فجأة. مع الحلقة تحرّك 20% فقط، وكلها ذهبت إلى الخادم الجديد.

import threading
import time

calls = 0
calls_lock = threading.Lock()
cache: dict[str, str] = {}
key_locks: dict[str, threading.Lock] = {}
key_locks_guard = threading.Lock()


def slow_db_query(key: str) -> str:
    global calls
    with calls_lock:
        calls += 1
    time.sleep(0.1)                     # expensive query
    return f"value-of-{key}"


def get_naive(key: str) -> str:
    if key in cache:
        return cache[key]
    value = slow_db_query(key)
    cache[key] = value
    return value


def get_single_flight(key: str) -> str:
    if key in cache:
        return cache[key]
    with key_locks_guard:
        lock = key_locks.setdefault(key, threading.Lock())
    with lock:                          # one loader per key
        if key in cache:                # filled while we waited
            return cache[key]
        value = slow_db_query(key)
        cache[key] = value
        return value


def simulate(getter, n_requests: int = 50) -> int:
    global calls
    calls = 0
    cache.clear()
    barrier = threading.Barrier(n_requests)

    def worker() -> None:
        barrier.wait()                  # all requests arrive together
        getter("merchant:m1")

    threads = [threading.Thread(target=worker) for _ in range(n_requests)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return calls


print("naive         -> DB queries:", simulate(get_naive))
print("single-flight -> DB queries:", simulate(get_single_flight))
naive -> DB queries: 50 single-flight -> DB queries: 1

الشرح سطرًا بسطر

  1. threading.Barrier(n_requests): تجعل كل الطلبات تنتظر ثم تنطلق معًا. هكذا نحاكي لحظة انتهاء الصلاحية.
  2. get_naive: كل طلب يجد الـ Cache فارغًا، فيذهب إلى قاعدة البيانات. 50 استعلامًا لنفس البيانات!
  3. key_locks.setdefault(...): قفل واحد لكل مفتاح. نحمي القاموس نفسه بقفل آخر.
  4. with lock: طلب واحد فقط يدخل. الباقون ينتظرون.
  5. if key in cache داخل القفل: هذا "الفحص المزدوج" (Double-Checked). من ينتظر يجد القيمة جاهزة بعد أن يدخل.
  6. في الإنتاج مع عدة خوادم، يكون القفل موزّعًا، مثل SET key NX EX في Redis.

الأخطاء الشائعة

1. اختراق الـ Cache: عدم حفظ "غير موجود"

مهاجم يرسل 1000 طلب لتاجر غير موجود: fake-999. ماذا يحدث؟

❌ الطريقة الخاطئة

db_reads = 0
DB = {"m1": "Cairo Store"}
cache: dict[str, str] = {}


def query_db(mid: str) -> str | None:

    db_reads += 1
    return DB.get(mid)

    if mid in cache:
        return cache[mid]
    row = query_db(mid)
    if row is not None:      # misses never cached
        cache[mid] = row
    return row

✅ الطريقة الصحيحة

db_reads = 0
DB = {"m1": "Cairo Store"}
NOT_FOUND = object()         # sentinel value
cache: dict[str, object] = {}


def query_db(mid: str) -> str | None:
    global db_reads
    db_reads += 1
    return DB.get(mid)


def get_merchant(mid: str) -> str | None:
    if mid in cache:
        value = cache[mid]
        return None if value is NOT_FOUND else value
    row = query_db(mid)
    cache[mid] = row if row is not None else NOT_FOUND
    return row

    get_merchant("fake-999")

⚠️ لماذا الطريقة الأولى خاطئة؟ الـ Cache يحفظ النتائج الموجودة فقط. كل طلب لمفتاح غير موجود يصل إلى قاعدة البيانات. المهاجم يستطيع إسقاط قاعدة البيانات بمفاتيح عشوائية. الحل: احفظ "غير موجود" أيضًا، مع TTL قصيرة (30–60 ثانية). وللحماية الأقوى استخدم Bloom Filter.

2. أخطاء أخرى شائعة

  • ❌ Cache بدون TTL: إذا فشل الإبطال مرة واحدة، تبقى البيانات القديمة للأبد. ✅ ضع TTL لكل مفتاح، حتى لو كانت طويلة.
  • ❌ نفس TTL لكل المفاتيح: ملأت الـ Cache عند التشغيل، فتنتهي كل المفاتيح بعد 5 دقائق بالضبط. هذا هو الانهيار الجماعي. ✅ أضف عشوائية صغيرة للـ TTL (Jitter).
  • ❌ الحذف قبل التحديث: يسبب بيانات قديمة كما رأينا في المخطط. ✅ حدّث قاعدة البيانات، ثم احذف.
  • ❌ اعتبار الـ Cache مصدر الحقيقة: Redis قد يُعاد تشغيله أو يُخرج المفاتيح. ✅ الكود يجب أن يعمل (أبطأ) إذا كان الـ Cache فارغًا تمامًا.
  • ❌ Cache محلي مع إبطال: حذفت المفتاح من خادم واحد، لكن 9 خوادم أخرى عندها نسخة قديمة. ✅ استخدم TTL قصيرة للـ Cache المحلي، أو Cache موزّعًا.

أفضل الممارسات

  • اعرف ماذا تحفظ. الـ Cache مفيد للبيانات التي تُقرأ كثيرًا وتتغير قليلًا. إعدادات التاجر: نعم. رصيد الحساب: لا.
  • صمّم أسماء المفاتيح بوضوح. مثل merchant:v2:m1. رقم الإصدار يسمح لك بإبطال كل المفاتيح القديمة عند تغيير شكل البيانات.
  • راقب نسبة الإصابة. إذا نزلت فجأة، فهناك مشكلة: إخراج كثير، أو مفاتيح خاطئة.
  • أضف Jitter للـ TTL. بدلًا من 300 ثانية بالضبط، استخدم رقمًا بين 270 و 330.
  • احمِ المفاتيح المشهورة. استخدم قفلًا لكل مفتاح (Single-Flight)، أو جدّد المفتاح قبل انتهائه.
  • اختر L7 للتوجيه الذكي، و L4 للسرعة القصوى. كثير من الأنظمة تستخدم L4 أمام مجموعة من موازنات L7.
  • اجعل فحص الصحة خفيفًا. إذا كان /health يشغّل استعلامًا ثقيلًا، فقد يسقط النظام بسبب الفحص نفسه.
💡 نصيحة لأنظمة الدفع: لا تحفظ رقم البطاقة الكامل في أي Cache أبدًا. معيار PCI DSS يفرض قيودًا صارمة على تخزين بيانات البطاقات. احفظ فقط توكن (Token) أو آخر 4 أرقام.

الأداء والموازنات

رياضيات نسبة الإصابة

مع Cache-Aside، كل طلب يسأل الـ Cache أولًا. عند الإخفاق، نضيف رحلة إلى قاعدة البيانات. إذا كانت \(h\) نسبة الإصابة:

$$T_{\text{eff}} = T_{\text{cache}} + (1 - h) \times T_{\text{db}}$$

والحمل على قاعدة البيانات هو فقط الطلبات التي أخفقت:

$$\text{DB QPS} = (1 - h) \times \text{Total QPS}$$

لاحظ شيئًا مهمًا: رفع نسبة الإصابة من 90% إلى 99% يبدو تحسنًا صغيرًا. لكنه يقلل حمل قاعدة البيانات 10 مرات، من 10% إلى 1%.

كم مفتاحًا يتحرك عند إضافة خادم؟

مع mod N، عند الانتقال من \(N\) إلى \(N+1\) خادم:

$$\text{moved}_{\text{mod}} = \frac{N}{N+1} \qquad \text{moved}_{\text{ring}} \approx \frac{1}{N+1}$$

مع 4 خوادم: \(4/5 = 80\%\) مقابل \(1/5 = 20\%\). هذا ما رأيناه في المثال 3 بالضبط.

مشروع تطبيقي صغير: خدمة إعدادات التاجر

ستبني خدمة تجمع كل ما تعلمته: LRU و TTL و Cache-Aside والإبطال وقياس نسبة الإصابة. ثم نشغّل سيناريو محددًا ونتابع كل خطوة.

from collections import OrderedDict
from dataclasses import dataclass


@dataclass
class Stats:
    hits: int = 0
    misses: int = 0

    @property
    def hit_ratio(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total else 0.0


class LRUTTLCache:
    def __init__(self, capacity: int, ttl: float, clock) -> None:
        self.capacity, self.ttl, self.clock = capacity, ttl, clock
        self._data: OrderedDict[str, tuple[str, float]] = OrderedDict()
        self.stats = Stats()

    def get(self, key: str) -> str | None:
        item = self._data.get(key)
        if item is None or self.clock() >= item[1]:
            self._data.pop(key, None)   # drop expired entry
            self.stats.misses += 1
            return None
        self._data.move_to_end(key)
        self.stats.hits += 1
        return item[0]

    def set(self, key: str, value: str) -> None:
        self._data[key] = (value, self.clock() + self.ttl)
        self._data.move_to_end(key)
        if len(self._data) > self.capacity:
            self._data.popitem(last=False)

    def delete(self, key: str) -> None:
        self._data.pop(key, None)


class MerchantService:
    def __init__(self, db: dict[str, str], cache: LRUTTLCache) -> None:
        self.db, self.cache = db, cache
        self.db_reads = 0

    def get(self, mid: str) -> str:
        if self.cache.get(mid) is not None:
            return "cache"
        self.db_reads += 1
        self.cache.set(mid, self.db[mid])
        return "db"

    def update(self, mid: str, value: str) -> str:
        self.db[mid] = value
        self.cache.delete(mid)
        return "invalidated"


now = [0]
cache = LRUTTLCache(capacity=2, ttl=30, clock=lambda: now[0])
svc = MerchantService({"A": "fee=2.5", "B": "fee=1.9", "C": "fee=3.0"}, cache)

events = [
    (0, "get", "A"), (1, "get", "A"), (2, "get", "B"),
    (3, "get", "A"), (4, "get", "C"), (5, "get", "A"),
    (6, "update", "A"), (7, "get", "A"),
    (40, "get", "A"), (41, "get", "A"), (42, "get", "B"),
]

for t, op, key in events:
    now[0] = t
    result = svc.get(key) if op == "get" else svc.update(key, "fee=2.0")
    print(f"t={t:>2} {op:<6} {key} -> {result}")

s = cache.stats
print(f"hits={s.hits} misses={s.misses} "
      f"hit_ratio={s.hit_ratio:.0%} db_reads={svc.db_reads}")

  2. t=1, t=3: A في الـ Cache. إصابة.
  3. t=4: نضيف C. السعة 2، فيخرج B لأنه الأقدم استخدامًا.

  5. t=7: إخفاق بسبب الإبطال. نجلب القيمة الجديدة. صلاحيتها حتى t=37.

اختبر نفسك

1. التطبيق يسأل الـ Cache، وعند الإخفاق يقرأ من قاعدة البيانات ثم يحفظ النتيجة. ما اسم هذه الاستراتيجية؟
2. عندك 4 خوادم Cache تستخدم hash % N. أضفت خادمًا خامسًا. كم مفتاحًا يتحرك تقريبًا؟
3. مفتاح مشهور انتهت صلاحيته، فوصلت آلاف الاستعلامات إلى قاعدة البيانات في نفس الثانية. ما اسم المشكلة؟
4. في بوابة دفع، أي بيانات لا يجب أن يكون الـ Cache مصدرها؟
5. نسبة الإصابة 95%، وزمن الـ Cache 1ms، وزمن قاعدة البيانات 40ms. ما متوسط زمن الاستجابة؟

تمارين

تمرين 1 (سهل): ما قيمة 9% إضافية؟

النظام يستقبل 10,000 قراءة في الثانية. زمن الـ Cache 1ms، وزمن قاعدة البيانات 20ms. احسب زمن الاستجابة وحمل قاعدة البيانات عند نسبة إصابة 90%، ثم 99%.

💡 تلميح

استخدم المعادلتين في قسم الأداء. نسبة الإخفاق = 1 − h.

✅ الحل 
def cache_effect(hit_ratio: float, qps: int = 10_000,
                 t_cache: float = 1, t_db: float = 20) -> tuple[float, float]:
    miss = 1 - hit_ratio
    return t_cache + miss * t_db, miss * qps


for h in (0.90, 0.99):
    latency, db_qps = cache_effect(h)
    print(f"hit={h:.0%}  latency={latency:.1f} ms  db_qps={db_qps:,.0f}")
hit=90% latency=3.0 ms db_qps=1,000 hit=99% latency=1.2 ms db_qps=100

الفرق في زمن الاستجابة صغير. لكن قاعدة البيانات ترتاح 10 مرات. هذا قد يعني خادم قاعدة بيانات واحدًا بدلًا من عشرة.

تمرين 2 (متوسط): التوزيع الدوري الموزون السلس

عندك خادم كبير وزنه 5، وخادمان صغيران وزن كل منهما 1. اكتب موازنًا يوزّع الطلبات حسب الأوزان. لا يجب أن يرسل 5 طلبات متتالية إلى الخادم الكبير، بل يوزّعها بسلاسة. هذه خوارزمية Nginx.

💡 تلميح

لكل خادم "وزن حالي" يبدأ من صفر. في كل طلب: أضف لكل خادم وزنه، واختر صاحب أكبر وزن حالي، ثم اطرح منه مجموع الأوزان.

✅ الحل 
class SmoothWeightedRR:
    def __init__(self, weights: dict[str, int]) -> None:
        self.weights = weights
        self.current = {s: 0 for s in weights}
        self.total = sum(weights.values())

    def next_server(self) -> str:
        for server, weight in self.weights.items():
            self.current[server] += weight
        best = max(self.current, key=self.current.__getitem__)
        self.current[best] -= self.total
        return best


lb = SmoothWeightedRR({"big": 5, "small-1": 1, "small-2": 1})
print([lb.next_server() for _ in range(7)])
['big', 'big', 'small-1', 'big', 'small-2', 'big', 'big']

الخادم الكبير أخذ 5 من 7، وكل صغير أخذ 1. والطلبات موزّعة بالتناوب وليست متجمعة. بعد 7 طلبات ترجع كل الأوزان الحالية إلى صفر وتبدأ الدورة من جديد.

تمرين 3 (متوسط): امنع الانهيار الجماعي

اكتب دالة ttl_with_jitter(base, spread) ترجع TTL عشوائية حول القيمة الأساسية. مثال: 300 ثانية ± 10%. ثم تأكد أن كل القيم داخل النطاق، وأنها ليست كلها متساوية.

💡 تلميح

استخدم random.uniform(-delta, delta). ومرّر كائن random.Random حتى تستطيع اختبار الدالة.

✅ الحل 
import random


def ttl_with_jitter(base: int, spread: float = 0.1,
                    rng: random.Random | None = None) -> int:
    rng = rng or random.Random()
    delta = base * spread
    return int(base + rng.uniform(-delta, delta))


rng = random.Random(42)
ttls = [ttl_with_jitter(300, 0.1, rng) for _ in range(1000)]
print(min(ttls) >= 270, max(ttls) <= 330, len(set(ttls)) > 1)
True True True

الآن المفاتيح التي دخلت الـ Cache معًا تنتهي في أوقات مختلفة، موزّعة على دقيقة كاملة. قاعدة البيانات تستقبل الحمل تدريجيًا بدلًا من ضربة واحدة.

تمرين 4 (صعب): خطة Cache لبوابة الدفع

لكل نوع من البيانات التالية، قرّر: هل نستخدم Cache؟ وما الاستراتيجية؟ وما الـ TTL؟

  1. إعدادات التاجر (الاسم، العمولة، طرق الدفع).
  2. أسعار تحويل العملات.
  3. حالة عملية الدفع (معلّقة، ناجحة، فاشلة).
  4. رصيد محفظة التاجر.
  5. بيانات البطاقة.
💡 تلميح

اسأل عن كل نوع: كم مرة يُقرأ؟ كم مرة يتغير؟ وما أسوأ شيء يحدث إذا كانت القيمة قديمة؟

البياناتالقرارالسبب

القاعدة العامة: كلما كانت القيمة القديمة أخطر، قلّت الـ TTL أو ألغيت الـ Cache.

الخلاصة

  • موازن L4 سريع ويرى العنوان والمنفذ فقط. موازن L7 يقرأ طلب HTTP ويوجّه بذكاء.
  • اختر الخوارزمية حسب الحالة: بالدور، أو بالأوزان، أو أقل اتصالات، أو التجزئة المتسقة.
  • التجزئة المتسقة تحرّك حوالي 1/(N+1) من المفاتيح فقط، مقابل N/(N+1) مع mod N.
  • Cache-Aside هي الاستراتيجية الأكثر شيوعًا: اقرأ من الـ Cache، وعند الإخفاق اقرأ من قاعدة البيانات واحفظ.
  • عند الكتابة: حدّث قاعدة البيانات، ثم احذف المفتاح. وضع TTL دائمًا.
  • LRU تحذف الأقدم استخدامًا، وتعمل بسرعة O(1).
  • احمِ النظام من التدافع بقفل لكل مفتاح، ومن الاختراق بحفظ "غير موجود"، ومن الانهيار الجماعي بـ Jitter.
  • رفع نسبة الإصابة من 90% إلى 99% يقلل حمل قاعدة البيانات 10 مرات.
  • لا تستخدم الـ Cache كمصدر حقيقة للأموال أو الأرصدة.
